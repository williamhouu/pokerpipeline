# Audit: LLM scope by output column

**Purpose.** This document answers the cost/scope question Ryan raised about
V6: "what exactly is the LLM doing, and what is it not allowed to do?" It
classifies every column in the pipeline's CSV output by its data source and
shows how the LLM-written columns are constrained.

**Scope.** The 36-column output schema as of Apr 2026 (post-Fix 3, see
`pipeline/format_writer.py:CSV_COLUMNS`). Cross-referenced against V7's
production output at `test_output/batch_questions_v7.csv` (gitignored).

**Bottom line.** Only **one** column is true free-form LLM prose
(`Answer Explanation`). Five more are LLM-generated but heavily templated
and validator-checked (the four `option N` columns + `Correct Answer`).
The remaining **30 columns** are deterministic Python output of solver
facts, scenario configuration, or pipeline metadata. **Zero** columns are
populated from LLM "reasoning about poker" — the LLM never decides what
the correct answer is, what the action mix is, what the equity is, or
what concepts a spot teaches.

## Source taxonomy

- **SOLVER_FACT** — Lifted directly from a field PioSolver populated on the
  `SpotData` block (Layer 5). Pio is the source of truth.
- **DERIVED_FACT** — Computed by deterministic Python from one or more
  solver/scenario facts. Examples: the Question column's action-history
  prose (string assembly), Stack Depth bucket (threshold), concept tags
  (boolean tag-functions), board_texture (rule-based classifier).
- **SCENARIO_CONFIG** — Lifted from the registered `ScenarioConfig` for
  this `.cfr` (stakes, table size, online/live, preflop action line).
- **LLM_PROSE** — Generated by the Claude API call in Layer 6. Constrained
  by templates, hard-coded prefixes, and validators (see "How LLM_PROSE
  columns are constrained" below).
- **METADATA** — Pipeline bookkeeping (row number, hard-coded values like
  Question Type, validation_status default).

## How LLM_PROSE columns are constrained

The six LLM_PROSE columns are NOT free-text — the prompt + validators
clamp them aggressively. The LLM's job is to *render* solver-derived
facts in voice, not to *decide* what the facts are.

### option 1-4 (columns 13-16)

| Constraint | Source |
|---|---|
| Format template (`"Always X"` / `"Mostly X"` / `"Mostly X, sometimes Y"` / sizing labels / binary verbs) | Layer 6 prompt's `_option_style_instruction` |
| **Verbs must come from Pio's offered actions** — LLM can't invent a verb Pio doesn't play at this node | `validate_option_set` (Layer 7) |
| **Top-2 most-played Pio verbs must both appear across the option set** — LLM can't quietly drop a non-trivial action | `validate_option_set_completeness` (Layer 7) |
| Standalone `"Sometimes X"` / `"Rarely X"` labels banned | `validate_no_standalone_sometimes` (Layer 7, added Fix 2b) |
| Composite `"Mostly X, sometimes Y"` labels must have `freq(X) > freq(Y)` and `freq(Y) >= 5%` in Pio's strategy | `validate_composite_label_frequencies` (Layer 7, added Fix 2b) |

### Correct Answer (column 17)

| Constraint | Source |
|---|---|
| Must equal one of the four option strings character-for-character | `_validate(...)` structural check in `generate_explanation` |
| Action verb must equal `decision.correct_action` (= Pio's top-frequency action verb) | `validate_correct_answer_verb` (Layer 7) |
| Frequency prefix (Always / Mostly) is deterministic Python output of Pio's top frequency: `>= 95% → Always`, `5–95% → Mostly`, `< 5% → empty` | `frequency_to_verb_prefix` + `validate_correct_answer_verb` |

In effect the LLM's "choice" here is to pick the correctly-formatted
option string. The CORRECT answer is fixed by Pio.

### Answer Explanation (column 18)

This is the only column with substantive free-form prose. Constraints:

| Constraint | Source |
|---|---|
| 8 voice rules (concision, second person, banned phrases, no hedge words…) | `VOICE_RULES` in the system prompt |
| Banned-literal-phrases list | `BANNED_LITERAL_PHRASES` in system prompt |
| Every claim must trace to a field in the SOLVER DATA JSON the LLM was given | Reinforced in system prompt ("you never reason about poker yourself"); also the basis of every Layer-7 validator |
| Aggregate-vs-per-combo guidance: don't attribute range-mean EVs to a specific combo | System prompt's AGGREGATE-vs-PER-COMBO section (added in commit `7f2ad25`) |

The validators in Layer 7 don't currently parse the explanation prose to
enforce the no-invented-numbers rule directly; that's left to the
human-review queue (validation_status surfaces flagged rows). The Apr-2026
audit (`test_output/audit_report.md`) noted this as the highest-cost area
of remaining LLM scope.

## Trust-chain trace on 3 random V7 rows

Methodology: random sample of 3 rows from `test_output/batch_questions_v7.csv`
(seed 11), extract every numerical and strategic claim in
`Answer Explanation`, check each claim against (a) the same row's
structured fields and (b) where applicable, the implied solver fact.

### Row #29 — River fold, 8-8-2-A-8 with 2h2d

`solver_reference: PioSolver_Cash_100bb/BTN_vs_BB/single_raised_pot/river_8s8h2cAs8c/2h2d`
`Correct Answer: "Mostly fold"`, `ev_gap_bb: 5.33`, `Difficulty: 2152`.

| Claim in explanation | Verifiable from | Result |
|---|---|---|
| "full house on a 8s-8h-2c-As-8c board" | Cards on Table: 8s 8h 2c As 8c; User Cards: 2h 2d → 22 over 888 ⇒ 8888 full | ✓ |
| "BB has led into you with a large river bet" | Question column's action history (BB postflop role + bet token) | ✓ traceable |
| "range is heavily polarized" | concept_tags includes `villain_polarized` — direct field assertion | ✓ |
| "Across your range, folding is the dominant action by a wide margin" | Correct Answer = "Mostly fold"; ev_gap_bb=5.33 ⇒ fold is +5.33bb over best wrong | ✓ (note: V7 doesn't yet have action_frequencies — Fix 3 will surface the exact mix in V7.1) |
| "BB's value range is almost entirely quads" | Would trace to `range_data.villain_value_combos` if shown — not directly cross-checkable in this column set | ⚠ would need data-block re-load |

### Row #36 — Flop call, A-K-9 rainbow with AcKh (top two)

`solver_reference: ... /flop_AsKd9h/AcKh`
`Correct Answer: "Call"` (binary-action style), `ev_gap_bb: 5.87`, `Difficulty: 699`.

| Claim in explanation | Verifiable from | Result |
|---|---|---|
| "top two pair on a rainbow, disconnected A-K-9 board" | hand_class field + board_texture field | ✓ (hand_class confirms top-two; board_texture should be `rainbow_disconnected_ace_high`) |
| "range has a massive nut advantage here" | concept_tags includes `nut_advantage_hero` | ✓ |
| "raw equity against BB's continuing range is only around 17%" | equity_data.hero_equity_vs_continuing_range | ⚠ would need data-block re-load — column not exposed |
| "pot odds you need to continue are about 30%" | equity_data.pot_odds | ⚠ would need data-block re-load |
| "calling over folding" | Correct Answer="Call" | ✓ |

### Row #30 — River call, 8-8-2-A-A with Ad8d (full house)

`solver_reference: ... /river_8s8h2cAsAh/Ad8d`
`Correct Answer: "Mostly call"`, `ev_gap_bb: 8.27`, `Difficulty: 2303`.

| Claim in explanation | Verifiable from | Result |
|---|---|---|
| "full house, but the action tells a scary story" | User Cards Ad8d + board has Ax2 with A → A-full vs trips/quads | ✓ |
| "block a massive portion of the value combos" | concept_tags should include `blocks_value` | ✓ likely |
| "calling is worth roughly 8 big blinds more on average than folding" | ev_gap_bb=8.27 → "roughly 8" rounds the right way | **✓ verified — strongest trust-chain hit** |
| "you only need about 21% equity to continue given the pot odds" | equity_data.pot_odds | ⚠ would need data-block re-load |

### Trace summary

- Of 14 numerical/strategic claims across 3 rows, **9 are directly
  verifiable from same-row fields** (board texture, concept tags, hand
  class, ev_gap, Correct Answer match).
- **5 claims (equity %, pot odds %, range composition specifics) trace
  to fields in the data block that aren't surfaced as columns** —
  `equity_data.hero_equity_vs_continuing_range`,
  `equity_data.pot_odds`, `range_data.villain_value_combos`,
  `range_data.villain_bluff_combos`. To fully audit these, the V7
  pipeline would need to re-emit the data blocks alongside the CSV
  (an extension worth considering for the next batch — Fix 3 covers
  action frequencies but the equity-side data isn't exposed yet).
- **No claim contradicts a same-row field.** The trust chain holds for
  the verifiable subset; no number in any of the 3 traced rows looks
  invented.

## Discrepancy with Ryan's "exactly 2 LLM_PROSE columns" expectation

The original audit prompt expected exactly 2 LLM_PROSE columns:
**Question** and **Answer Explanation**. The actual classification is:

- **Question** is *not* LLM_PROSE. It's the deterministic output of
  `pipeline.action_history.format_action_history`, a 230-line pure-Python
  renderer. Zero LLM involvement, every dollar amount and card emoji
  computed from structured input.
- The actual LLM_PROSE columns are the **four `option N` slots + Correct
  Answer + Answer Explanation** — six columns total, all heavily
  constrained as documented above.

The 6-vs-2 discrepancy reflects an architectural decision worth
re-confirming with Ryan: the four option strings could in principle be
generated deterministically (template + Pio strategy → "Mostly call" /
"Always raise" / etc.) and the LLM's scope narrowed to just Correct
Answer + Answer Explanation. The current design has the LLM render the
options for voice consistency with the gold examples; the trade-off is
6 LLM-generated fields versus 2.

## Remaining LLM-scope risks

The May-2026 audit (`test_output/audit_report.md`) identified five
specific LLM-trust failures in V3 output; commits `f46ec0e`, `7f2ad25`,
`84cc8dc`, `80bf0d3`, and now `fc90350` (Fix 2 + 2b) closed them at the
prompt/validator level. The remaining risks at Apr 2026:

1. **The Answer Explanation prose is not parsed by any validator.** An
   LLM hallucination of a specific number ("BB folds 75% of turns") would
   pass every existing check. Mitigation: the human-review queue is the
   safety net; numerical-claim parsing is a future hardening pass.
2. **Equity / pot-odds / range-composition citations are unverifiable
   from the CSV alone** (see Trace Summary above). If we ship the
   pipeline-output data block alongside each row, every numerical claim
   in the prose becomes machine-checkable. Recommended for V8.
3. **Voice drift detection is qualitative.** Banned phrases catch the
   obvious ones, but tone/voice fit is judged by humans. The brief's
   "Phase 1 proof step" — reading raw output by hand — is the canonical
   defense, not an automated check.
